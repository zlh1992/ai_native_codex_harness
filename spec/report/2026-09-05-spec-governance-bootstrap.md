## 背景

项目已有 README 和操作文档，但没有一个能区分长期架构约束、发布契约与带日期实施结论的规范体系。先前审计、修复方案和验证证据散落在对话与文档中，后续修改容易丢失决策背景或把未实现建议当成现状。

这是治理机制的 bootstrap：仓库此前没有“计划先于修改”的报告约束，因此本报告与首批 spec 在同一变更中建立；从本次完成后开始，后续修改必须先建报告。

## 目标与非目标

### 目标

- 建立架构索引和按职责拆分的当前架构规格。
- 集中定义产品、运行、协议、文件、数据、容量和发布约束。
- 把自动 HTTP E2E、其他 gate 用例和真实公网冒烟分别记录。
- 提供报告流程、模板和当前实现基线。
- 通过根 `AGENTS.md` 与 README 入口让后续修改者能够发现并执行规范。

### 非目标

- 本次不改变业务代码、数据库 schema、HTTP API 或运行参数。
- 不把历史审计原文直接复制为当前架构；只保留已核实且仍有效的结论。
- 不新增文档生成器或外部依赖。

## 实施计划

1. 盘点 README、现有 docs、原审计、代码 schema、运行状态与测试门控。
2. 建立 `spec/architecture/index.md` 和总览、组件、约束、领域、安全、执行、恢复、E2E、运维专题。
3. 建立 `spec/report/index.md`、模板、当前实现基线与本次治理报告。
4. 新增根 `AGENTS.md`，把变更报告和架构同步设为仓库规则。
5. 从 README/旧架构文档链接 canonical spec。
6. 校验全部相对 Markdown 链接、格式和仓库门控，再填写最终结论。

## 实际改动

- 新增 `spec/index.md`，定义规范入口、事实优先级和规范用语。
- 新增 `spec/architecture/index.md` 及 9 个专题，覆盖架构决策、组件、强制约束、领域不变量、安全、执行生命周期、持久化恢复、E2E 契约和运维演进。
- 新增 `spec/report/index.md`、强制模板、当前实现基线和本报告，将长期约束与 point-in-time 事实分离。
- 新增根 `AGENTS.md`，要求每次仓库修改先写计划、完成后写实际结果和结论；架构/E2E 变化必须同步 spec。
- README 增加 spec/report 入口，旧 `docs/ARCHITECTURE.md` 标明 canonical 架构位置。
- 本次只修改规范和导航，没有改变业务代码、数据库、API、配置或运行服务。

## 结论

请求范围已经完成。项目现在有一个 canonical 架构入口、明确编号的强制约束、可维护的 E2E 发布契约，以及每次修改必须使用的计划/结论报告流程。本报告本身完成了“计划—实施—验证—结论”的首个闭环示例。

这套治理不改变当前运行语义，可以与既有 README 和操作 docs 并存；后续修改者从根 `AGENTS.md` 即可发现并执行要求。

## 遗留事项

- 当前没有 CI 层的“每个 commit 必须修改 report”差异检查；仓库通过 `AGENTS.md` 强制代理工作流，通过评审确认人工变更。若未来接入 CI，可基于 base/head changed-files 再增加自动检查。
