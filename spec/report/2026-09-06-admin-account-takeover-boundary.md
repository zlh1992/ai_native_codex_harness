## 背景与证据

需求方确认当前产品信任超级管理员：其账号默认不拥有员工未分享项目的直接内容 ACL，但可在受限的管理员用户更新流程中设置员工新密码。旧会话随后失效；使用员工身份与新密码重新登录后，系统按该员工既有权限授予访问。这是受支持的账号接管/恢复能力，不是管理员内容路由的 ACL 绕过，也不是密码破解。

静态代码核对显示，管理员用户更新路由可以写入员工密码哈希，并在改密后删除该员工会话、排空其运行；内容路由仍从会话用户重新解析 project access。宿主 macOS 账号可直接读取其管理的磁盘文件，因而不受 Portal Web ACL 的保密承诺约束。本次不新增运行验证，结论仅基于当前工作树静态审查。

## 目标与非目标

### 目标

- 将“直接内容 ACL”与“超级管理员可接管员工账号”的区别写成长期架构约束。
- 明确系统不承诺对超级管理员或宿主机管理者的内容保密隔离。
- 保持既有设计：管理员不能以自己的会话直接读取员工未分享项目。

### 非目标

- 不移除或收紧当前管理员密码重置能力。
- 不新增员工自助重置、OIDC、MFA 或独立验证渠道。
- 不改变宿主操作系统或磁盘权限模型，不声称 Portal ACL 能限制宿主机管理者。
- 不修改实现、数据库迁移、公开 API 或自动化测试。

## 约束与风险

- 遵守 `PRD-002`、`DAT-004`、`DAT-006`、`DEV-001`、`DEV-002`、`DEV-003` 与 `DEV-006`。

## 结论

目标已达成。规格现在清楚区分三项事实：老板自己的管理员会话不能直接访问员工未分享项目；受信任的超级管理员可改密并以员工身份重新登录，从而按员工 ACL 查看内容；宿主 Mac 管理者不受 Portal ACL 限制。该设计与内部互信 Pilot 的既有产品决策一致，可以发布。

## 遗留事项

- 若未来业务要求员工内容对超级管理员保密，需单独设计只由员工掌握的身份验证/恢复渠道，并引入独立 OS 身份、存储与执行环境；这超出当前内部互信 Pilot 的范围。
